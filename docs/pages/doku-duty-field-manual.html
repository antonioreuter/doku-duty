Doku Duty Field Manual

How a change travels from a loose idea to a merged spec. Read once; after that it is three commands.

The mechanism

Two drawers, one filing clerk

The whole workflow is a rule about where things live. openspec/changes/ is scratch — everything in it is provisional and gets thrown away. openspec/specs/ is the permanent record. Archive is the only command that writes to it.

Convenient: the game already has words for this. A provisional note is a hypothesis under test, in turquoise. A settled note is one you have derived, in indigo. The two drawers below are coloured to match.

Before you plan

Which document wins

They overlap on purpose. Only one is authoritative for each thing, and when two disagree this table decides.

Worth knowing

Only openspec/config.yaml is injected into every artifact prompt automatically. Everything else is read on request — so when a document matters to a change, name the file explicitly.

The loop

Starting a change

  1. Pick from the backlog

    openspec/BACKLOG.md is dependency-ordered across six milestones. Take the lowest-numbered change whose dependencies are done. Do not start Milestone 2 work because it sounds more fun — the ordering is the schedule.

    Each entry gives the change name, its capability, the decisions it implements, and a Watch for line naming how that change usually goes wrong. Read that line before you plan, not after.

  2. Check the decisions are settled

    Open the D-NN ids the entry cites. If the change needs a decision nobody has made, stop and run /grill-with-docs as its own session first. A proposal is not where decisions get made.

  3. Propose

    /opsx:propose add-notes    # step-by-step
/opsx:ff add-notes         # same artifacts, one pass

    Use ff when the change is well understood and you want momentum; propose when you want to read each artifact as it lands.

  4. Build

    /opsx:apply works the list top to bottom. Tick each box the moment it is done, not in a batch — solo project, nobody else can reconstruct where you stopped.

  5. Archive

    /opsx:archive folds the delta into openspec/specs/. That directory is the thing you are actually accumulating.

What you get

Three artifacts, no design doc

The custom doku-lite schema produces three artifacts instead of four. design.md is gone; its questions live inside the proposal template as three prompts — grid performance, offline / cold start / app kill, and new dependency — that you answer only where they apply.

When to skip specs

Set skip_specs: true in the change's .openspec.yaml when nothing a player or another capability can observe changes — refactors, dependency bumps, CI work. Anything observable needs a spec. When in doubt, write it: an unnecessary requirement is cheaper than a capability with no record.

Two rules from practice

Run /grill-with-docs on its own, before the change exists. Nested inside a spec-driven workflow it runs the interview but silently writes no files.

Its output belongs in docs/DECISIONS.md and openspec/project.md, not the CONTEXT.md and docs/adr/ it defaults to. The config redirects it. If either of those ever appears, the redirect stopped working.

Sharp edges

Things that will bite you

  • /opsx:verify does not exist here. The installed workflows are propose, explore, apply, ff, sync, archive. Add more with openspec config set workflows '[...]' then openspec update.
  • The skills live in the plugin cache, not this repo. Editing them is possible, but a plugin update overwrites your edits.
  • rules: must be a list of strings. Write it as a | block and OpenSpec silently discards every rule. Check for must be an array of strings warnings after editing.
  • Capability names are permanent. They become openspec/specs/<name>/ and lib/features/<name>/. Rename before the first archive, or not at all.
  • The colour count is stated inconsistently across docs/DESIGN.md, docs/SPEC.md, docs/DECISIONS.md and the config. docs/DESIGN.md wins. Reconcile the rest before add-design-system is built.

Before you trust it

Checking the setup is sound

openspec doctor                      # root health
openspec schema validate doku-lite   # schema and templates
openspec list                        # active changes
openspec context                     # watch for parse warnings

Zero warnings from openspec context is the signal your rules are actually reaching the agent rather than being dropped on the floor.
